# 찬양대회 운영·복구 기준

## 확정한 기준

2026년 10월 1~15일 접수, 1~18일 투표, 19일 수상 확정 후 수상자·계좌를 확인하여 순차 지급.
브라우저당 한국 시간 하루 1표. 같은 날 취소 후 재선택 가능. 여러 브라우저의 동일인 식별은 보장하지 않는다.
접수 마감에 공개 적격 작품 5개 이하면 자동 취소. 취소 결정은 고정하며 투표·시상 없음.
좋아요 동점은 등록 시각과 등록 번호 순. 지급정보는 관리자만 열람한다.

## 운영자가 사용하는 화면

- /admin/praise-contest: 접수 검토, 권리·공개 상태, 전화·계좌 열람, 지급 관리.
- /contact: 접수·투표·영상 권리·개인정보 관련 문의 창구. 문의 처리와 공개·보류 사유를 관리 기록에 남긴다.
- /praise-contest: 실제 모집과 투표.
- /praise-contest/preview: 체험용. 실제 참가·집계·송금과 분리되어 있다.

## 19일 지급 준비 순서

1. 마감 결과 생성과 반복 조회 시 동일성 확인.
2. 투표 수와 투표 생성·취소 이벤트 합계 대조. 불일치가 있으면 지급 예약 차단.
3. 수상자·영상 권리·접수 문의와 예금주·계좌 확인. 계좌 입력이 은행 실명 확인을 뜻하지 않는다.
4. 이체 처리 예약. 같은 수상자·순위는 중복 예약할 수 없다.
5. 은행에서 실제 이체한 뒤 거래번호 기록. 이 사이트가 은행 이체를 실행하지 않는다.
6. 응답 지연 등으로 결과가 불명확하면 처리 중 상태 유지. 은행에서 미입금을 확인한 경우에만 실패로 기록하고 재예약.
7. 지급 완료 기록은 다시 수정·예약하지 않는다. 이전 예약의 늦은 요청은 attempt_id로 차단한다.

## 문의·이의 대응

문의 내용, 해당 참가 영상, 접수 시각, 근거, 처리 사유를 먼저 확인한다. 공개 댓글로 연락처·계좌를 설명하지 않는다.
권리 분쟁 영상은 사유를 기록하고 보류한다. 마감 이후 공개 중단은 기존 확정 순위를 임의로 다시 매기지 않는다.
이미 처리 중인 지급은 영상 공개 여부와 별개로 은행 결과를 기록할 수 있다.
미해결 수상 이의가 있으면 해당 건을 지급 예약하지 않는다. 참가자별 접수·수상 제한은 확정 후 참가 안내에 반영해야 한다.

## 복구와 비밀값 관리

전화·계좌 암호문은 ADMIN_SESSION_SECRET에서 분리된 용도로 파생한 AES-GCM 키를 사용한다. 관리자 비밀번호 변경과 이 비밀값 변경은 별개다.
ADMIN_SESSION_SECRET을 바꾸기 전에 이전 키를 안전하게 보존하고 격리된 환경에서 기존 암호문의 복호화·새 키 재암호화·복원 검증을 끝내야 한다. 단순 키 교체는 기존 계좌 복호화를 깨뜨린다.
운영 DB 백업 파일에는 개인정보와 암호문이 있으므로 저장·복사·전달을 승인된 접근 범위로 제한한다. 소스 저장소에 넣지 않는다.
복구 순서: 복원 대상 시점 확인 → 별도 DB로 복원 → 무결성/행수/투표 이벤트/결과 snapshot/지급 예약 확인 → 검증 후 운영 전환.
현재 실행한 복구 검사는 가상의 SQLite 백업·복원이며 Cloudflare 운영 DB 복구 실증을 대신하지 않는다. 운영 복원·키 변경은 미실행이다.

## 다음 회차

이번 회차 ID praise-2026-10과 지급 기록을 재사용하지 않는다. 다음 일정·상금·규칙 버전과 별도 ID를 확정한 뒤 접수 전 동일 테스트를 다시 실행한다.
현 구현은 10월 회차 기준이다. 자동 월별 생성·이전 회차 전용 조회 화면은 추가 구현이 필요하다. 이번 홍보에 월별 개최 확정을 쓰지 않는다.

## 검증 범위

실제 라우트를 실행한 로컬 HTTP 테스트: 가짜 Cloudflare env/D1 adapter, 가상 개인정보, 고정 시각, oEmbed 대체 응답 사용.
운영 환경에서는 공개 GET 정상, 관리자 지급정보 비로그인 요청 403을 확인. 실제 운영 참가 등록·투표 부하·은행 이체는 미실행.
완료한 테스트 수와 명령은 이번 실행 기록을 따르며, 코드 수정 후 관련 테스트를 재실행한다.
